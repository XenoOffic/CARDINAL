# Security Policy

## Overview

Security is a fundamental part of the CARDINAL project.

CARDINAL is intended to include components capable of:

- Executing code
- Managing files
- Communicating over networks
- Running AI models
- Managing agents
- Performing automated experiments
- Generating and testing code
- Running sandboxed workloads
- Performing controlled system modifications

Because of this, security must be considered throughout the architecture and development process.

---

# Supported Versions

CARDINAL is currently under active development.

Until the project reaches a stable release, security fixes will generally target the latest development version.

| Version | Supported |
|---|---|
| Development / main | Yes |
| Older development versions | Best effort |
| Unreleased versions | No |

---

# Reporting a Vulnerability

Please **do not publicly disclose security vulnerabilities through GitHub Issues**.

A vulnerability report should be handled privately whenever possible.

If GitHub Security Advisories are enabled for this repository, please use the private security advisory mechanism.

If they are not available, contact the project maintainers through the private contact method specified by the repository.

---

# What to Include

A useful security report should contain:

- A clear description of the vulnerability.
- The affected component.
- The affected version or commit.
- Steps required to reproduce the issue.
- Expected behavior.
- Actual behavior.
- Potential security impact.
- Proof of concept, when appropriate.
- Possible mitigation, if known.

Please avoid including real secrets, credentials, private keys, or personal information in vulnerability reports.

Security Principles

CARDINAL should follow several fundamental security principles.

Least Privilege

Components should receive only the permissions they actually require.


---

Isolation

Untrusted or experimental workloads should be isolated from the host system whenever possible.


---

Explicit Capabilities

Sensitive operations should require explicit capabilities or permissions.

Examples include:

filesystem.read
filesystem.write
network.connect
process.spawn
runtime.execute
system.modify


---

Resource Limits

Untrusted workloads should have appropriate limits for:

CPU

Memory

Disk

Processes

Threads

Network usage

Execution time



---

Auditability

Security-sensitive operations should be observable and traceable.

Important events should generate appropriate audit information.


---

Defense in Depth

CARDINAL should not rely on a single security mechanism.

Multiple independent layers should be used when practical.


---

Sandbox Security

CARDINAL may execute generated or experimental code inside sandboxed environments.

Sandbox implementations should consider:

Filesystem isolation

Network isolation

Process isolation

Resource limits

Permission boundaries

Execution timeouts

Environment isolation

Secret isolation

Escape prevention


A sandbox should never be considered secure merely because code was generated by an AI system.


---

AI-Generated Code

CARDINAL may generate code automatically.

AI-generated code must be treated as untrusted until it has been:

1. Parsed or validated.


2. Tested.


3. Executed in an appropriate environment.


4. Checked for regressions.


5. Evaluated against security policies.



Generated code must not automatically receive unrestricted system privileges.


---

Controlled Self-Improvement

CARDINAL may eventually include systems capable of proposing and testing modifications to itself.

Self-improvement must operate through controlled mechanisms.

A proposed modification should follow a process similar to:

Analyze
   ↓
Generate Proposal
   ↓
Create Candidate
   ↓
Sandbox
   ↓
Run Tests
   ↓
Run Security Checks
   ↓
Run Regression Tests
   ↓
Benchmark
   ↓
Evaluate
   ↓
Version
   ↓
Rollback if Necessary

A generated modification must not automatically become part of the trusted system solely because it passes a single evaluation.

Important changes should remain traceable and reversible.


---

Secrets

Never commit sensitive information to the repository.

This includes:

API keys

Passwords

Authentication tokens

Private keys

Cloud credentials

Database credentials

Access tokens

Personal credentials


Use environment variables or an appropriate secret-management system instead.

Local secret files should remain excluded by .gitignore.


---

Dependencies

Dependencies should be reviewed before being introduced into security-sensitive components.

Consider:

Known vulnerabilities

Maintenance status

License

Dependency chain

Update frequency

Project reputation

Required permissions

Attack surface


Security updates should be applied when reasonably possible.


---

Supply Chain Security

CARDINAL should eventually implement appropriate supply-chain protections, including where practical:

Dependency auditing

Lockfiles

Reproducible builds

Integrity verification

Automated vulnerability scanning

Signed releases

Build provenance



---

Authentication and Authorization

Components providing APIs, distributed execution, dashboards, or remote control should use appropriate authentication and authorization mechanisms.

Authentication alone is not sufficient.

Authorization should determine what an authenticated identity is actually allowed to do.


---

Network Security

Network-enabled components should follow secure-by-default principles.

Avoid:

Unauthenticated administrative interfaces

Unrestricted remote execution

Unnecessary exposed ports

Hard-coded credentials

Insecure communication protocols


Network capabilities should be explicitly controlled where possible.


---

Data Protection

CARDINAL may process potentially sensitive information.

Systems handling user or application data should minimize unnecessary collection, storage, and exposure of data.

Sensitive information should not be written to logs unless explicitly required and appropriately protected.


---

Logging and Auditing

Security-relevant events should be logged appropriately.

Examples include:

Authentication failures
Permission changes
Sandbox violations
Capability requests
Privilege changes
Remote execution
Security policy violations
Configuration changes
Self-modification attempts
Rollback events

Logs should avoid exposing secrets or sensitive information.


---

Responsible Disclosure

Security vulnerabilities should be reported privately whenever possible.

After a vulnerability has been investigated and a fix or mitigation is available, the maintainers may publish appropriate information about the issue.

The timing and level of disclosure should consider:

Severity

Availability of a fix

User impact

Exploitability

Potential ongoing exploitation



---

Security Research

Security research and responsible experimentation are welcome.

Researchers should avoid:

Accessing data that does not belong to them.

Destroying data.

Disrupting infrastructure.

Attempting to compromise unrelated systems.

Exposing private information.

Using CARDINAL to attack third-party systems.


Testing should be performed against systems for which the researcher has authorization.


---

Emergency Security Issues

For critical vulnerabilities involving active exploitation or significant system compromise, use the fastest available private communication channel with the maintainers.

Do not publish exploit details before maintainers have had a reasonable opportunity to investigate.

Disclaimer
